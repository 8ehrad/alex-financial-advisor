# Security, guardrails, observability, and operations

## Authentication and authorization

### Main application

1. Clerk handles sign-in/sign-up in the browser and issues a session JWT.
2. The frontend gets the token from Clerk and sends `Authorization: Bearer <JWT>` to `/api/*`.
3. API Gateway is a proxy, not the JWT verifier. FastAPI's `ClerkHTTPBearer` validates the token against the configured Clerk JWKS endpoint. The API uses the verified `sub` claim as `clerk_user_id`.
4. Handlers scope collection queries by that identity and check the owner of an account, position's parent account, or analysis job before returning or mutating it.

The browser's signed-in components are UI behavior only. Authorization is enforced on the backend. The bare Lambda `/health` endpoint has no Clerk dependency but is not routed by the deployed API Gateway, which only exposes `/api/{proxy+}`.

### Research ingestion

The researcher Lambda Function URL has `authorization_type = "NONE"`; it is publicly callable. Its research endpoints can invoke Bedrock and send content to ingestion. The ingestion REST endpoint uses API Gateway API-key/usage-plan enforcement and the researcher sends the key in the `x-api-key` header. The API key is stored in Terraform/Lambda configuration as a sensitive setting, but it is not an end-user identity system.

### Cloud and data boundaries

- Database passwords are generated by Terraform and stored in Secrets Manager. Lambda roles retrieve the secret and use the RDS Data API; clients do not receive database credentials.
- Lambda IAM roles grant database, queue, model, vector, and invoke access according to component needs. The main app and agent database access references the Aurora cluster and specific secret. The researcher Bedrock policy and SageMaker's managed `AmazonSageMakerFullAccess` role are broader than an ideal production least-privilege policy.
- The frontend S3 website bucket is public-read so CloudFront can serve static assets. It contains exported frontend files, not user portfolio rows.
- The ordinary ingestion S3 bucket has versioning, AES-256 server-side encryption, and public access blocking. The S3 Vectors index is controlled by its own IAM API permissions.
- CloudFront viewer traffic is HTTPS-only. Its S3 website origin uses HTTP between CloudFront and the website endpoint; API Gateway origin uses HTTPS.

## Guardrails that exist in code/configuration

- Clerk JWT verification and owner checks on portfolio CRUD and analysis jobs.
- Pydantic request schemas for account, position, and profile values; the shared schemas apply bounds to several numeric fields and use typed enums for allocations.
- API Gateway throttling configured at 100 requests/second with a burst limit of 100 for the main HTTP API.
- The ingestion REST API key usage plan is configured for 100 requests/second, a burst of 200, and a quota of 10,000 requests/month. API keys identify a calling application and are not user authentication.
- API requests carry normal HTTP status codes and JSON error bodies. The CloudFront static-path rewrite only attaches to the default S3 behavior; it does not rewrite the `/api/*` behavior.
- SQS retains messages for one day, long-polls, uses a visibility timeout slightly longer than the planner timeout, and moves repeatedly failing messages to a DLQ after three receives.
- Planner Lambda timeout is 15 minutes; specialist Lambdas use bounded timeouts. Agent runs have max-turn limits and retry transient model throttles in several handlers.
- The Reporter optionally evaluates its report with a judge and applies a score floor when the Langfuse observability client is available.
- UI warns that the generated content is AI-created and not vetted by a qualified financial advisor. The code does not make this a regulated advice or execution product.

These controls reduce accidental and cross-user access; they are not a comprehensive production security review.

## Known limitations and interview-worthy gaps

1. **Public research endpoint:** no auth on the Lambda URL, so anyone who finds it may invoke costly research. Add authentication, throttling, and abuse controls before treating it as production.
2. **Market-price fallback:** if `POLYGON_API_KEY` is empty or Polygon errors, `backend/planner/prices.py` returns a random number from 1 to 100. Analysis can therefore run, but price-derived totals are not trustworthy in that configuration. The current deployment used no Polygon key.
3. **Research API key handling:** the researcher uses an API key to ingest. It is a shared service credential; rotate it through the deployment config and avoid exposing it in logs or support output.
4. **Development-grade database recovery:** one-day backup retention, `skip_final_snapshot = true`, no Performance Insights, and minimum Aurora capacity can be acceptable for a demo but need production recovery/cost choices.
5. **Local Terraform state:** each stack uses a separate local state file. Stack 7 reads local state from stacks 5 and 6. This is convenient for a demo but fragile for collaboration and CI/CD; state is not a remote team backend.
6. **Terraform state contains sensitive values:** `sensitive = true` masks values in CLI output; it does not encrypt values in local state. State can contain the generated database password, API key, or other secret inputs. Protect local state and backups, and never commit them.
7. **SQS retry behavior is weaker than the queue policy suggests:** the Planner records the job as failed, then catches orchestration errors and returns a `statusCode: 500` object from its SQS Lambda handler. Lambda treats a normal handler return as a successful invocation; SQS may delete that message instead of retrying it. The DLQ is reliably used only when the invocation itself fails/times out (or the handler is changed to report batch item failures / re-raise). Do not claim every failed job is retried three times.
8. **Completion does not guarantee every result exists:** Planner marks a job complete when its agent run returns. Specialist tool errors can be returned as text to the model, and the handler does not enforce that report, charts, and retirement payloads are all present before marking completion.
9. **No CI/CD pipeline:** packaging, Terraform, frontend build/upload, and invalidation are run from scripts or manually.
10. **Observability is mixed:** CloudWatch logs/metrics and two dashboards are provisioned. Langfuse is optional and is not initialized if the relevant secret key is absent. When enabled, evaluate whether financial prompts/results may be exported to the configured Langfuse service. Dashboards show service metrics; they are not paging alarms or a full distributed trace guarantee.
11. **CORS breadth:** the API Gateway HTTP API declares `*` origins (without credentials); FastAPI sets its own configured origin list. CORS controls browser behavior and is not authentication.
12. **Model controls:** prompts contain task and browsing constraints, but there is no comprehensive model-output validation, suitability assessment, or guaranteed human approval before a financial interpretation is displayed.
13. **Shared knowledge index:** the deployment reuses an existing `financial-research` S3 Vectors index rather than creating it in Terraform. Its lifecycle and ownership are outside the ingestion stack's state.

## Observability

### CloudWatch

- Lambda handlers use Python logging; Lambda streams output to CloudWatch Logs.
- Agent log groups are `/aws/lambda/alex-planner`, `alex-tagger`, `alex-reporter`, `alex-charter`, and `alex-retirement`, with seven-day retention in stack 6.
- API, ingestion, researcher, and other functions also produce Lambda logs; check their actual log-group retention in AWS because configuration differs by stack.
- `alex-ai-model-usage` covers Bedrock invocations/errors, input/output tokens and latency, plus SageMaker invocation and latency metrics.
- `alex-agent-performance` compares Lambda execution duration, errors, invocations, and concurrency/throttle-related metrics for the five analysis agents.
- CloudWatch standard Lambda/API/SQS metrics are available. The stack does not configure SNS paging alarms or an incident-management service.

### Langfuse

Agent modules wrap runs in `observe()`. If `LANGFUSE_SECRET_KEY` is configured, they instrument the OpenAI Agents SDK with Logfire and export traces to Langfuse; otherwise they log that observability is skipped. Flush adds a blocking delay (about 10–15 seconds in the current helper modules), which can increase Lambda duration/cost when enabled. `OPENAI_API_KEY` may also be needed by the trace integration even though inference itself uses Bedrock.

### Practical debugging path

1. Confirm caller/region: `aws sts get-caller-identity` and check `eu-west-2`.
2. Check API Lambda logs for request/auth/database errors; use the API's response status and request ID.
3. For a job, inspect the Aurora `jobs` row first (`status`, `error_message`, timestamps and result payload fields).
4. Check SQS visible/in-flight counts and `alex-analysis-jobs-dlq` for invocation-level failures; a job marked failed may not have been retried because of the Planner handler behavior above.
5. Follow the job ID across planner and specialist CloudWatch log streams.
6. For model failures, check Bedrock access/model quotas and the CloudWatch AI dashboard. For missing knowledge results, verify SageMaker is `InService`, then check the `financial-research` index and IAM access.
7. For web app/API routing, check CloudFront behavior selection and API Gateway logs. The static frontend behavior and `/api/*` behavior have different origins.

## Deployment and local operation

### AWS deployment

Prerequisites: AWS CLI credentials, Terraform, Docker, Node/npm, Python/uv, account-level model access and configured Clerk application.

Terraform directories are independent. Each requires local `terraform.tfvars`; sensitive configuration and state are gitignored. Existing stack 7 uses local state outputs from stacks 5 and 6. Do not commit state, tfvars, `.env`, Clerk secrets, API-key values, or database credentials.

Common layer order:

1. Build and apply SageMaker (`2_sagemaker`).
2. Apply ingestion (`3_ingestion`) and provide an existing S3 Vectors bucket/index and SageMaker endpoint.
3. Apply Aurora (`5_database`), then run `backend/database/run_migrations.py` and `seed_data.py` with cluster/secret/region environment variables.
4. Apply agents (`6_agents`) with database, vector, embedding, model and optional provider/observability values; packages are uploaded via the stack's S3 package bucket.
5. Build/push/deploy researcher (`4_researcher`) if desired; its scheduler is optional and disabled in the deployed configuration.
6. Package API and apply frontend/API (`7_frontend`); build Next.js with Clerk public key configuration, upload `frontend/out` to its bucket, invalidate CloudFront.
7. Apply enterprise dashboards (`8_enterprise`).

`scripts/deploy.py` documents and automates the stack 7 API packaging, Terraform apply, frontend build, S3 upload and invalidation sequence. It assumes upstream stacks and required local files already exist. Review it before use: it deletes current frontend bucket objects before upload.

### Local development

Create ignored root `.env` and `frontend/.env.local` from examples, configure Clerk, and run `scripts/run_local.py`. It starts the FastAPI dev server on port 8000 and Next.js on 3000. Local API data access still needs AWS credentials and Aurora variables unless you mock the database. Local agent tests and AWS integration tests are separate; the deployed integration diagnostic is `cd backend && uv run test_full.py`.

### Costs and lifecycle

Aurora Serverless v2 is the main standing cost; the deployed Terraform output estimated approximately $43/month minimum for the configured 0.5–1 ACU cluster at deployment time. SageMaker serverless inference, Bedrock tokens, Lambda duration, NAT/networking, logs, and CloudFront can add usage-based cost. The public researcher endpoint can be invoked by anyone and can generate costs. Check current AWS pricing and Cost Explorer for actual charges.
